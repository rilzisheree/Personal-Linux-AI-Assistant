Fix the **response cutoff/truncation bug** in my local AI assistant **Lura**. This is now a high-priority bug.

## CURRENT PROBLEM

Lura frequently starts generating a perfectly valid response but stops abruptly in the middle of a sentence.

Examples observed:

```text
...making
```

```text
On an NVIDIA RTX
```

```text
...system has been up for roughly 223
```

```text
...currently used at 49%
```

Web-search responses also get cut off, for example:

```text
DLSS 5 Confirmation: The company has officially confirmed the launch of DL
```

and:

```text
...Linux kernel release is roughly 2
```

The problem is NOT simply that Lura is unable to answer the question. It begins answering correctly and then terminates prematurely.

This has happened with:

* normal model responses
* GPU/system-information responses
* full system-status responses
* web-search responses
* long explanations
* multi-tool responses

Short responses sometimes work normally.

## IMPORTANT CONTEXT

A previous investigation already looked at the GPU path and found a GPU parser defect involving malformed `nvidia-smi` rows. That parser was fixed.

However, the response cutoff **still occurs**, including with responses that do not depend on the GPU parser.

Therefore:

**DO NOT assume the GPU parser is the root cause.**

Do not undo the GPU parser fix.

Also do not modify the web-search provider as part of this task.

The routing issue where casual questions unnecessarily triggered web search has also already been fixed.

Focus specifically on the response lifecycle.

---

# TRACE THE ENTIRE RESPONSE PIPELINE

Inspect the actual implementation from beginning to end:

```text
USER REQUEST
↓
ROUTER
↓
TOOL EXECUTION (if any)
↓
MAIN MODEL REQUEST
↓
OLLAMA API
↓
OLLAMA STREAM
↓
BACKEND STREAM PROCESSING
↓
SSE / HTTP / IPC
↓
FRONTEND RECEIVER
↓
MESSAGE ACCUMULATION
↓
FINAL DISPLAY
```

Find exactly where the response is being truncated.

Do not guess.

Determine whether the model itself is stopping, or whether Lura is stopping/discarding the response.

---

# FIRST TEST: RAW OLLAMA VS LURA

This is extremely important.

Run the main model directly through the existing Ollama interface/API with a prompt designed to produce a long response.

Then run the exact same/similar prompt through Lura.

Compare:

```text
RAW OLLAMA OUTPUT
LURA OUTPUT
```

Determine:

```text
Did Ollama itself stop?
OR
Did Lura stop receiving/displaying tokens?
```

If Ollama produces the complete response while Lura truncates it, the bug is definitely somewhere in Lura's pipeline.

Do not change token limits blindly before determining this.

---

# INVESTIGATE OLLAMA REQUEST PARAMETERS

Inspect every parameter sent to Ollama.

Especially:

* `num_predict`
* `num_ctx`
* `temperature`
* `stop`
* `stream`
* model name
* timeout
* keep_alive
* any max token/output limit
* any response length limit
* any internal token budget
* any cancellation signal

Look for accidental values such as:

```text
num_predict = 100
num_predict = 256
num_predict = 512
```

or anything else that could explain the repeated early termination.

Also inspect whether a `stop` sequence is accidentally matching ordinary text.

Do NOT simply increase token limits without understanding the existing configuration.

---

# INVESTIGATE STREAMING

Inspect all streaming code.

Look for:

* generators ending early
* `return` inside stream loops
* `break` conditions
* exception handlers swallowing errors
* async task cancellation
* timeout expiration
* connection closure
* SSE termination
* incorrect `[DONE]` handling
* frontend treating a temporary event as final
* only consuming the first chunk
* incorrect JSON parsing
* dropped chunks
* race conditions
* queue exhaustion
* background worker termination
* task cancellation after tool execution
* response state being overwritten
* frontend replacing accumulated text instead of appending
* duplicate/final event handling
* stream buffers being flushed incorrectly

Pay particular attention to code that does something equivalent to:

```python
return
break
cancel()
close()
```

inside or immediately around the streaming loop.

Instrument the stream temporarily so we can determine:

```text
OLLAMA_CHUNKS_RECEIVED = N

OLLAMA_DONE_REASON = ...

```

If possible, record the Ollama response's actual completion metadata, including the model's stop reason.

We need to know whether termination is:

```text
completed normally
length limit
stop sequence
cancelled
timeout
connection error
parser error
unknown
```

Do not hide this information.

If an exception occurs after partial output, preserve the partial output but clearly record the error internally.

