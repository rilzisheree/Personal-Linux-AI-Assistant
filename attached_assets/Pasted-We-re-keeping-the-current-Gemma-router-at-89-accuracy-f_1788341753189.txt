## 2. Make application launching Flatpak-aware

This is very important.

I use Flatpak for roughly 95% of my desktop applications.

Luna currently tries to use incorrect launch commands.

Build an application discovery system instead of hard-coding random commands.

At startup or during setup, discover installed applications using the appropriate Linux commands, including Flatpak applications.

For Flatpak specifically, discover:

* Application ID
* Display name
* Installed status
* Launch command

For example, Luna should be able to understand:

"Open Discord"

and resolve that to the actual installed Flatpak application rather than guessing a binary name.

Use the system's actual installed application data.

Prefer:

```text
flatpak list
```

and appropriate Flatpak launch commands such as:

```text
flatpak run <APPLICATION_ID>
```

rather than assuming the application has a normal executable in PATH.

Also support normal native applications when they exist.

Create an application registry/cache if useful, but refresh it when necessary so newly installed apps can be discovered.

The goal is:

```text
User: "Open Discord"
        ↓
Luna identifies Discord
        ↓
Find installed application
        ↓
Determine whether it is Flatpak/native
        ↓
Run the correct command
```

Do NOT make Luna guess commands when the application can be discovered from the system.

# 4. Replace click-to-confirm with voice confirmation

Currently Luna sometimes displays a confirmation UI where I have to click OK before she executes a command.

I want to replace this with a **voice confirmation system**.

For commands that require confirmation:

Luna should say something like:

> "Sir, may I shut down the computer?"

Then I can answer:

> "Yes."

or:

> "No."

The application should detect the answer and either execute or cancel the pending action.

Do NOT require me to click a confirmation button for normal command execution.

The confirmation should happen through voice whenever possible.

# 5. Create permission levels

Do NOT simply give Luna unrestricted shell access.

Create a permission/risk system.

### LEVEL 0 — Read-only / automatically allowed

No confirmation required.

Examples:

```text
nvidia-smi
lscpu
free
df
uptime
uname
ls
ps
flatpak list
checking GPU status
checking CPU status
checking RAM
checking disk space
checking system information
listing windows
listing installed apps
```

These should execute automatically.

### LEVEL 1 — Normal reversible actions

Generally allow automatically when they are clearly requested.

Examples:

```text
Open Discord
Open Firefox
Close Spotify
Set volume
Change brightness
Take screenshot
Open a website
```

If an action is potentially disruptive, it can still request confirmation.

### LEVEL 2 — Potentially disruptive actions

Require voice confirmation.

Examples:

```text
Restart an application
Kill a process
Delete temporary files
Change important system settings
Modify configuration
Install/remove software
```

Luna should ask:

> "Sir, may I do that?"

and wait for a voice response.

### LEVEL 3 — Dangerous/destructive actions

ALWAYS require explicit voice confirmation.

Examples:

```text
Shut down PC
Reboot PC
Delete files
Format drives
Modify partitions
Run destructive shell commands
Change security settings
```

For these, Luna must NEVER execute automatically.

# 6. Confirmation must be tied to the exact command

Do NOT accept an old "yes" for a different command.

Example:

Luna:

> "Sir, may I shut down the computer?"

User:

> "Yes."

→ Execute shutdown.

But if the user says:

> "Yes"

after the confirmation has expired or there is no pending confirmation:

→ Ignore it as a command authorization.

Use a short expiration window for pending confirmations.

Also cancel the confirmation if the user says something unrelated.

---

# 7. Never blindly execute arbitrary LLM-generated shell commands

This is critical.

The LLM should NOT be able to generate arbitrary shell commands and immediately execute them.

Instead, create a controlled tool layer.

For example:

```text
open_app(app)
close_app(app)
restart_app(app)
get_gpu_status()
get_cpu_status()
get_memory_status()
get_disk_status()
get_system_info()
get_processes()
get_windows()
take_screenshot()
set_volume(level)
shutdown()
reboot()
```

The LLM requests a tool/action.

The application decides whether that tool is allowed automatically or requires confirmation.

This should be enforced by application code, not by the LLM's system prompt.

# 8. Make Luna's responses shorter

I don't want Luna constantly giving long responses.

Default to concise, natural answers.

For simple requests:

> "Done, Sir."

> "Discord is open."

> "Your GPU is at 58°C."

> "You have 12 GB of RAM available."

> "I'm listening."

Only give detailed explanations when:

1. I explicitly ask for details.
2. The task genuinely requires explanation.
3. The information would otherwise be unclear.

Avoid repeating my entire request.

Avoid unnecessary introductions.

Avoid saying things like:

> "Certainly! I'd be happy to assist you with that."

Instead:

> "Sure, Sir."

Keep spoken responses especially concise because Luna reads them aloud.

# 9. Voice and chat should stay synchronized

Luna currently responds both in chat and through voice.

Keep both channels synchronized.

The text response should be available in the chat UI.

The spoken response should use the same semantic response but can be slightly shortened if appropriate for speech.

Do NOT make Luna speak technical JSON, emojis, markdown formatting, tool names, or shell commands.

```text

```

Luna's voice should NOT say:

> "GPU utilization 42 percent fire emoji."

Strip emojis, markdown, code formatting, and other non-speech elements before TTS.
